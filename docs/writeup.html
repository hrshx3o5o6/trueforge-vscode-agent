2. Starting point

Forked sst/opencode, subdirectory sdks/vscode/, commit 521ceac004e59fbbfca0929596107cd8430f2b26. The official extension is a thin terminal launcher; we built the webview chat/diff-review UI and the entire TrueForge SDK integration ourselves on top of its activation scaffolding. The upstream extension's own agent loop was removed entirely — every action the agent takes runs through a TrueForge session, never a direct model-provider call.

3. Architecture on TrueForge

The extension's webview panel sends user turns to TrueForge's SDK (sessions.createTurnStream), which streams back model text and tool-call events. Editor capabilities are exposed to the agent as real MCP tools served by an in-process MCP server (it needs vscode.* symbol/definition APIs, so it cannot run standalone) — the agent decides what to read/edit, not our extension code.

The six MCP tools: repo_map, search_code, read_file (read-only) and propose_edit, run_terminal_command (approval-gated, orange in the diagram), plus go_to_definition which wraps VS Code's own executeDefinitionProvider — editor-native and far cheaper than grep for "where is X actually defined," a genuine differentiator versus grep-only forks.

TrueForge's own native tool-approval mechanism drives the diff-review flow — we did not build a separate approval system. propose_edit returns a diff and is marked needs-approval; TrueForge's tool.approval_required event pauses the turn until the extension's approval handler resolves it, and only then does vscode.workspace.applyEdit (per accepted hunk, undo-stack integrated) touch disk. This is also what makes cancellation safe: if a turn is cancelled before approval, nothing was ever written.

Connector registration is fully automatic: on activation the extension starts the MCP server with a fresh bearer token and self-registers it with TrueForge; the agent definition (coding-agent.json) attaches it by name.

4. How context is selected

Two layers, by design. Layer 1 (before the turn): the editor assembles a small, budgeted opening bid under trueforgeAgent.contextTokenBudget (default 6,000 tokens) — explicit @file/@symbol mentions first, then automatic retrieval for agent mode: ripgrep keyword counts, IDF × BM25-style saturated scoring with file-length normalisation, one reserved slot each for the best source/test/doc file (tests and docs sharing a name stem with the top source file are boosted), and only ±2-line windows around matches — never whole files. Layer 2: the agent's own tools carry hard per-call budgets — repo_map capped at 4,000 tokens (directory tree + top-level symbols only, via VS Code's own DocumentSymbolProvider, cached and invalidated on save), read_file capped at 200 lines per call (no range on a large file returns an outline, never the full text), search_code capped at 20 results / ~300 chars per snippet.

The panel renders a visible "Context selected" card listing every file chosen, why, and its token cost — on pallets/flask 3.1.3 with the real Task B wording it selects src/flask/cli.py, tests/test_cli.py and docs/cli.rst in about 4.4k tokens, well under budget. Total tool-context per turn stays under ~10k tokens even on this 17k-line repo. This design is also where B4's "meaningful subagent use" comes from: a scout subagent calls only the read-only tools and hands a condensed summary to a separate editing agent — one coherent design covering both B1 and B4, not two bolted-on features.

8. Known limitations and what we'd do with another month

  • No OCR or non-text context handling (images, scanned docs) — everything is text/code only.
  • go_to_definition is only as accurate as the language server's own resolution on Flask's codebase; it inherits any gaps in VS Code's Python/Jedi support rather than fixing them.
  • The scout/editor subagent split is a fixed 2-stage pipeline, not a decision the agent makes dynamically itself — a month more would make this an agent-driven choice via TrueForge's dynamic subagent support, rather than hardcoded in our extension.
  • No automated test suite for the MCP server tools themselves (repo_map, search_code, etc.) — they were verified through live, repeated manual runs against the real Flask fixture, not unit tests. This is the most honest gap: correctness rests on rehearsal, not CI.
  • Context retrieval's keyword scoring (IDF × BM25-style) is tuned by inspection on one repo (Flask); it has not been validated against a second, structurally different codebase, so its token-budget behaviour on e.g. a monorepo or a non-Python project is unverified.
